# NapCat QQ 宠物接口失效说明（2026-08-11）

## 结论

NapCat 本身仍然能够登录 QQ、发送 OIDB 封包并收到服务器回包，但 QQ 宠物服务器已经开始校验请求所属的客户端 AppID/规则类型。电脑版 QQ 会话调用宠物 OIDB 时，服务器真实返回：

```text
errorCode=319
[oidb] rule type not match appid
```

因此，问题不是宠物 ID 错误、QQ 掉线、OneBot 端口断开，也不是简单更换某条 `OidbSvcTrpcTcp` 命令就能恢复。`petId` 只标识宠物；服务器还会依据 QQ 登录会话中的 AppID、QUA 和客户端类型判断该命令是否允许执行。

## 为什么旧版只显示“返回空响应”

NapCat 4.18.4 的 `send_packet` 链路存在第二个独立问题：QQ Native 层已经收到服务器回包，但 `sendSsoCmdReqByContend()` 暴露的 `rspbuffer` 为空，OneBot 最终把它显示成“空响应”。

本项目已通过精确命令监听补齐这段回包交接，并显式发送 `rsp: true`。传输修复后，隐藏在空响应后的服务器错误才被完整显示出来。这个修复能够让报错真实可见，但不能解除服务器的 AppID 策略。

## 观测时间

- 2026-08-11 16:03:55（北京时间）：同一电脑会话仍收到 2785 字节的学习结算响应，服务器验证成功。
- 2026-08-11 16:07:15：`0x96f2_1` 开始持续失败，此后没有恢复。
- 修复 NapCat 回包交接后：确认失败不是无回包，而是服务器返回 `errorCode=319`。

据此只能确认该账号/线路在 **16:03:55—16:07:15** 之间开始持续受到限制。更早已有间歇性空响应，因此不排除服务器按账号、线路或会话灰度下发；该时间不能视为腾讯全量发布规则的精确时刻。公开渠道没有找到对应公告，错误中附带的说明链接属于腾讯内部 iWiki，外部无法访问。

## 当前替代方案

最新版完全停用 NapCat/OneBot 作为 QQ 宠物协议通道，改用 MuMu 模拟器内真实 Android QQ 会话：

1. MuMu 12 中登录手机 QQ，并在模拟器设置中开启 Root 权限。
2. 启动器自动发现 MuMu ADB 和当前在线实例，不再要求手动填写固定端口。
3. 缺少手机协议运行组件时，只从 Frida 官方 Release 下载固定版本，并校验 SHA-256 后安装到模拟器。
4. 通过严格命令白名单加载手机规则；写操作只发送一次，超时后先查询服务器状态，不自动重复提交。
5. 调度器不会在手机协议断开后回退到 NapCat，避免再次使用已被拒绝的电脑版 AppID。

MuMu、手机 QQ 和协议组件必须保持运行。项目不会伪造 Android AppID、QUA 或设备身份，也不会导出、上传 QQ 会话。

## 版本影响

- `v1.3.0` 及更早的 NapCat 版本：不再适合作为 QQ 宠物任务通道。
- MuMu 手机规则版：作为当前最新版和推荐替代版本。
- NapCat 仍可用于其正常支持的 OneBot 场景，但不再被本项目用于 QQ 宠物 OIDB。
